# Safety model

Hands asks a person with no electronics experience to wire circuits that a language model
designed. The model is never trusted with safety. Deterministic code decides, using datasheet
numbers, and that decision is a **hard gate**: no wiring step and no USB power without it.

> **Scope.** Low-voltage only. Everything runs from a computer's USB port (5 V, 500 mA). Hands
> refuses mains power, batteries (LiPo, Li-ion, 18650, 9 V), anything above 5 V, and high-current
> loads (motors, solenoids, relays, heaters, LED strips). These limits are hard-coded in
> `hands/safety.py`. Editing `starter_kit.yaml` can make them stricter but never looser.

## The gates

| # | Gate | Code | What it blocks |
|---|------|------|----------------|
| 0 | Spec screen | `safety.screen_text` | Refuses a spec about mains, batteries, >5 V, >500 mA, motors, relays, heaters or lasers before any model call. The same screen runs on any model-written instruction to the human. |
| 1 | Rule check | `rules.require_safe` | Any design with an `error` finding. `layout.place()` and `wiring.build_guide()` both call it again, so no code path turns an unchecked design into wiring steps. |
| 2 | Photo check | `agent.stage_photo_check` + `wiring.compare` | USB power before the latest wiring matches the plan. Any physical change resets it. |
| 3 | Smoke test | `agent.stage_power_on` | Every power-on starts with safe-idle firmware (all GPIO inputs) and an INA219 reading of the 3V3 rail. Over budget, or a board that stops answering, means unplug right away. |
| 4 | Firmware lint | `fwlint.lint_firmware` | Firmware that drives pins outside the rule-checked `pin_map`, drives a button pin as an output, computes pin numbers, uses unlisted imports, `eval`/`exec`/dunder access, raw register writes (`machine.mem32`), deep sleep, overclocking, or bus peripherals on default pins. Runs again inside `_flash()` and in the MCP `flash_firmware` tool. |
| 5 | Fix validation | `agent.validate_fix` | Model-suggested physical changes that don't restore the approved plan. The model can only ask to re-seat a planned wire, re-check a placed part, or inspect the rails. The text the human sees is generated by code. |
| 6 | Test-plan validation | `agent.validate_test_plan` | Tests that toggle GPIOs outside the design or a pin wired to a button, press non-buttons, use bad regexes, or wait or measure too long. |

The agent also enforces these rules:

- Every physical change happens **with USB unplugged** (`_human_change` refuses while powered).
- After a change: photo check, then smoke test, then the app firmware goes back on.
- Before the first wiring step, the bare Pico gets safe-idle firmware. A real Pico keeps its
  last `main.py`, and an old program could otherwise drive pins into the new circuit.

Regression tests for every gate are in `tests/test_gates.py` and `tests/test_safety.py`.

## Hard limits and their sources

> **Verification status.** The values and section numbers below were written from memory of
> the RP2040, RP2350, Pico W and part datasheets during development. They were chosen to be
> conservative, but they **have not yet been re-checked line by line against the current
> PDFs**. Do that before relying on them, especially for the Pico 2 W (RP2350).

| Limit | Value | Source |
|-------|-------|--------|
| GPIO logic level | 3.3 V; GPIOs treated as **not 5 V tolerant** | Pico W datasheet §3.2: I/O is "fixed at 3.3 V", and GPIO26-29 inputs must not exceed IOVDD + ~300 mV. RP2350 (Pico 2 W) GPIOs are 5 V tolerant only while powered. Hands applies the stricter RP2040 rule to both. |
| Per-pin current | 12 mA max, 8 mA "comfortable" (warning) | RP2040 datasheet §2.19 / §5.5 (pad drive strength 2/4/8/12 mA; output levels are specified at the selected drive). RP2350 pads have the same 2/4/8/12 mA settings. |
| Total GPIO current | 50 mA | RP2040 datasheet §5.5 (IO electrical characteristics): maximum total IOVDD current. Applied to RP2350 as well. **Verify against the RP2350 datasheet's electrical chapter before relying on it for a Pico 2 W.** |
| 3V3(OUT) load | 300 mA (rail load + GPIO current) | Pico W datasheet §2.1: "it is recommended to keep the load on this pin under 300 mA". |
| USB budget | 500 mA total: 5 V rail + 3V3 regulator input (85 % efficiency assumed) + 100 mA for the Pico W itself | USB 2.0 spec: 500 mA per configured high-power port. Pico W datasheet §2.1/§3.4: VBUS 5 V ±10 %, Schottky diode to VSYS (1.8-5.5 V). |
| Max supply voltage | 5.25 V | USB VBUS upper tolerance. No part may need more than this (`module_power`). |
| Resistor dissipation | ≤ 125 mW (half of 1/4 W) | Standard derating for 1/4 W through-hole resistors. |

## Part facts (`hands/data/starter_kit.yaml`)

| Part | Values used | Source / reasoning |
|------|-------------|--------------------|
| 5 mm LEDs | Vf typ. 2.0 / 2.1 / 2.2 V (red/yellow/green). Worst-case current uses **Vf min 1.8 / 1.9 / 1.9 V**. I max 20 mA | Typical 5 mm indicator LED datasheets (e.g. Kingbright WP7113 series: Vf typ 2.0-2.2 V, recommended 20 mA). A lower Vf means more current, so the minimum is the safe bound. True-green, blue and white LEDs (~2.8-3.2 V) draw less current. |
| Series resistor | 220 Ω on GPIO: (3.3 − 1.8) / 220 = **6.8 mA**. From 5 V: (5 − 1.8) / 220 = 14.5 mA (< 20 mA) | Ohm's law. Checked by the `led_current` and `gpio_current` rules. |
| PN2222A NPN | E-B-C (flat face toward you); Vbe 0.7 V; Ic limit 600 mA (derated) | onsemi PN2222A datasheet: Ic 1.0 A abs. max, hFE min 75 @ 10 mA, VBE(sat) ≤ 1.2 V @ 150 mA, pinout "EBC". |
| Base resistor | 1 kΩ: Ib = (3.3 − 0.7) / 1000 = **2.6 mA**. That is within the GPIO limit and is a forced β of about 10 for a 25 mA buzzer (hard saturation). | The rule warns when Ib < Ic / 10, and errors when the base has no resistor or the collector has no load. |
| Active buzzer | 25 mA at 3.3-5 V (3.0-5.5 V range) | Typical 12 mm "5 V active buzzer" modules draw ≤ 30 mA. Above the 12 mA GPIO limit, so it needs the transistor. |
| SG90 servo | 4.8-6 V; idle 10 mA; moving 100-250 mA; stall **650 mA assumed** | Vendor specs list 4.8-6 V. Measured stall current varies from ~360 mA (Protosupplies) to 650-750 mA (common reports), so Hands assumes the high end. It must be on the 5 V (VBUS) rail, never on 3V3. Stall above the USB budget is a **warning**: don't hold the horn, and unplug if the Pico keeps resetting. |
| INA219 | Supply 3.0-5.5 V; 0.1 Ω shunt; PGA /8 = ±320 mV → ±3.2 A; shunt LSB 10 µV (0.1 mA); bus LSB 4 mV (bits 15..3); default config 0x399F | TI INA219 datasheet §7.1 (VS abs. max 6 V; IN± −0.3 to 26 V), §7.5, §8.5.1, Table 4, §8.6.2.1. Hands only measures the 3.3 V rail, so it is far inside these limits. |
| DHT22 module | 3.3-6 V, ~1.5 mA, on-board pull-up | Aosong AM2302 datasheet (3.3-6 V supply). The module's pull-up goes to its VCC, so on 5 V it would put 5 V on the GPIO. The `overvoltage` rule refuses that. |
| SSD1306 OLED module | 3.3-5 V, ~15 mA, I2C 0x3C, on-board pull-ups | Common module boards. Same pull-up hazard as the DHT22, so it must be powered from 3V3. |
| Pico W internal GPIO | GP23, GP24, GP25, GP29 not usable | Pico W datasheet §2.1 (wireless chip power/SPI/CS, VSYS sense). |
| Bench-reserved GPIO | GP26 / GP27 (INA219 I2C) | Hands' bench fixture. |

## The rules (`hands rules` prints them)

| Rule | Refuses |
|------|---------|
| `structure` | Unknown parts or part kinds with no rules (e.g. a relay added to the YAML); fixture/tool parts used as design parts; **direct use of any non-GPIO Pico pin** (3V3, VBUS, VSYS, RUN, 3V3_EN, ADC_VREF, GND: the fixture wires power); fixture net names (`V3_SRC` is the *unmeasured* 3.3 V, `INA_SDA/SCL`); **power-alias net names** (`Gnd`, `VCC`, `+5V`, …); bad names; malformed JSON types |
| `inventory` | More parts than you own |
| `pin_conflict` | Reserved/internal GPIO; one pin assigned twice; a wired GPIO missing from `pin_map` (the linter could not check it) |
| `power_short` | A net tying two supplies together |
| `gpio_short` | A GPIO wired straight to a supply/GND, or two GPIOs tied together |
| `shorted_part` | Both legs of a part on one net; a **button between two supplies** (pressing it shorts USB) |
| `unconnected_pin` | Floating part pins |
| `led_resistor` | An LED with no series resistor |
| `led_polarity` | An LED facing the wrong way |
| `led_current` | Worst-case LED current above its rating |
| `gpio_current` | Per-pin > 12 mA, or total > 50 mA (worst-case Vf; counts source and sink) |
| `transistor` | Emitter not on GND; base on a GPIO/supply with no resistor; **collector straight to a supply** (no load); collector load above Ic limit; warns on weak base drive |
| `buzzer_polarity` | A buzzer facing the wrong way |
| `servo_power` | Servo on 3V3 or on anything other than 5 V; no shared GND; signal not on a GPIO |
| `module_power` | Module supply outside its range; a part needing more than USB 5 V |
| `i2c` | Invalid SDA/SCL pair; swapped lines; two pin pairs on one controller; duplicate addresses; no pull-ups |
| `dht` | DHT data not on a GPIO; missing pull-up |
| `overvoltage` | **Any path that puts 5 V on a GPIO**, through a resistor, LED, buzzer or button (up to 4 hops), or through a module's on-board pull-ups when it is powered from 5 V |
| `resistor_power` | A resistor dissipating more than 125 mW worst case |
| `rail_budget` | 3V3 regulator load above 300 mA; total USB draw above 500 mA; warns on servo stall |

## Bypasses found in review (all fixed, all regression-tested)

1. **Power through Pico pins.** A design could wire `pico.VSYS` or `pico.VBUS` into its own net, and those nets were not checked as rails. A design could also tie `pico.3V3_EN` or `pico.RUN` to GND. Now only `pico.GPn` may appear.
2. **The fixture's unmeasured rail.** A net named `V3_SRC` was silently overwritten when the fixture was merged in. A net named `INA_SDA` joined the instrument's bus. Both names are now reserved.
3. **Alias rails.** `"Gnd"` or `"VCC"` was treated as a signal net the checker could not reason about. These names are now refused.
4. **Unknown parts.** Any YAML part kind was accepted, and the rules simply ignored it. Kinds are now an allow-list.
5. **Loosened YAML limits.** Setting `gpio_max_ma: 100` made the checker accept it. Limits are now clamped to hard ceilings.
6. **Button across supplies.** A button between 3V3 and GND passed every rule. It is now `shorted_part`.
7. **5 V into a GPIO.** 5 V could reach a GPIO through an LED, a buzzer, or a DHT22's on-board pull-up. Only resistors were checked before. Now `overvoltage` covers all of these.
8. **Collector to a supply.** An NPN with its collector straight on a supply has nothing to limit its current. Now `transistor` refuses it.
9. **Firmware lint gaps.** `Pin(n)` with a computed `n`, `from machine import Pin as P`, `machine.mem32`, `I2C(1)` on default pins, and `getattr(x, "__dict__")` all bypassed the linter. All are now refused.
10. **LLM fix path.** A model's `ask_human` diagnosis could tell the person to make *any* wiring change, while USB was plugged in, with no follow-up check. Now it is restricted to restoring the plan, with power off, followed by a photo check and a smoke test.
11. **Re-power without checks.** Hardware fixes found by the signal walk or the I2C/DHT checks plugged USB back in with no photo check or smoke test. Some of those changes were even made while powered. That no longer happens.
12. **Diagnostic toggling.** The signal walk toggled whatever GPIO the model's test plan named, including a button pin, which would short when pressed. That GPIO is now validated.
13. **MCP flashing.** The MCP `flash_firmware` tool flashed anything. It now needs a rule-checked design and lint-clean code.
14. **Web UI injection.** Vision-model text was put into the page with `innerHTML`. It is now inserted as text only, with a strict CSP, upload checks, and an access token whenever the UI is reachable beyond localhost.

## What the software cannot guarantee

- A vision model can wrongly say that wiring matches the plan. The INA219 smoke test is the
  backstop for shorts on the measured 3V3 rail. It does **not** see the 5 V servo rail or
  GPIO-driven loads. Watch the board at power-on and unplug if anything gets hot.
- Part values come from the YAML. If your parts differ (a clone with a different INA219 pin
  order, or a 100 Ω resistor in the 220 Ω bag), the checks are only as good as that file.
- USB ports differ. Most have current limiting, but some do not. A powered USB hub between
  the computer and the Pico adds protection for the computer.
- The simulator runs model-written firmware with restricted builtins. That is **not a
  security sandbox**. The firmware linter is the real gate.
