# Security and safety policy

Hands puts circuits designed by a language model into the hands of people with no electronics
experience. Physical safety is the primary concern; software security comes second. This file
is the threat model. The electrical safety rules and their datasheet sources are in
[`docs/safety.md`](docs/safety.md).

## Reporting a problem

If you find a way for a design, firmware image, instruction or web request to get past a
safety gate, **do not open a public issue with a working bypass**. Use GitHub's private
vulnerability reporting on this repository (Security tab, "Report a vulnerability"). Include
the design JSON or firmware, the command you ran and `hands --version`. Expect an answer within
7 days. Anything that could hurt a person or a computer is fixed first, with a regression test.

Ordinary bugs (a crash, a wrong hole in a diagram) are welcome as normal issues.

## Scope

In scope: `hands` itself, the rule checker, the firmware linter, the agent's gates, the web UI,
the MCP server and the simulator. Out of scope: the Anthropic, Ollama or OpenAI-compatible
servers you point it at, your USB hardware, and MicroPython itself.

## Assets

1. **The person.** Burns, a battery fire, a mains shock. Hands refuses every source of
   energy that could do this (gate 0 and the part allow-list); the remaining risk is a hot
   component on a 5 V USB port.
2. **The computer's USB port and the Pico.** Shorts, 5 V on a 3.3 V pin, too much current.
3. **The API key.** `ANTHROPIC_API_KEY` or an OpenAI-compatible key.
4. **The session data.** Photos of the person's desk, metrics logs, replay files.

## Trust boundaries and threats

| Boundary | Untrusted input | Threat | Mitigation |
|---|---|---|---|
| Spec -> agent | The user's sentence | Asks for mains, batteries, motors, >5 V | `safety.screen_text` refuses before any model call (gate 0). |
| Model -> design | Design JSON | Unsafe circuit; aliasing Pico power pins; parts outside the kit | Strict parsing, 20 deterministic rules, hard limits that YAML can only tighten, part-kind allow-list (gate 1). Re-checked with a digest before every physical stage. |
| Model -> firmware | `main.py` source | Drives unchecked pins, raw registers, `eval`, deep sleep, bootloader | AST linter (gate 4), run again inside every flash path including MCP. |
| Model -> person | Instructions, fixes | "Move the red wire to VBUS", changes while powered | Model fixes may only *restore the approved plan* (gate 5); the text shown is generated by code; any model hint passes the spec screen; every change happens with USB unplugged. |
| Model -> bench | Test plans | Toggle a button pin (short), long waits | `validate_test_plan` (gate 6). |
| Camera / vision model -> agent | Photos, VLM output | "Looks fine" when it is not | VLM output is sanitised and can only make the check fail; the smoke test on power-on is the backstop. |
| Simulator | Model firmware run in-process | Code execution on the host | Restricted builtins and an import allow-list. **Not a sandbox.** Do not run the simulator on firmware from a model you do not trust on a machine you care about; the RP2040 emulator bench runs firmware inside the emulated chip instead. |
| Browser -> web UI | HTTP requests | Remote control of the guide; XSS from model text | Binds to 127.0.0.1 by default. Beyond localhost a random access token is required. Strict CSP, no inline scripts, all server strings inserted with `textContent`, upload type and size checks. |
| MCP client -> bench | Tool calls | Flash arbitrary code, power on unchecked wiring | `flash_firmware` needs a rule-checked design and lint-clean code; `power_cut` is always allowed. |
| Hands -> model API | Prompts, photos | Key leakage | The key is read from the environment only, never written to disk, logs, metrics, replays or `hands doctor` output (`hands.log.redact` scrubs anything key-shaped). Photos are sent only when a vision model is configured. |
| Network feeds | ESPN scoreboard JSON | Malformed data | Parsed defensively; only `SCORE <n> <n>` lines reach the Pico. |

## Data handling

- `metrics/runs.jsonl` holds events and timings, no photos and no keys. Participant ids are
  whatever you pass (`--participant P01`); use pseudonyms (see `docs/study-protocol.md`).
- Replay files (`--record`) contain prompts and model replies. They contain no key. Review one
  before publishing it: a free-text spec you typed is in it.
- Photos taken for photo checks stay in the bench's working directory and are never uploaded
  unless a vision model is configured.

## What the software cannot guarantee

See the last section of [`docs/safety.md`](docs/safety.md): wrong part values in the YAML, a
vision model that misses something, loads the INA219 cannot see, USB ports without current
limiting. Watch the board at power-on and unplug if anything gets warm.
